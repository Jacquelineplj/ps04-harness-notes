MC-EvoBench: Auditing Experience-Driven Self-Improvement in Minecraft Agents
Abstract
A central challenge in embodied recursive self-improvement is enabling agents to convert interaction history into capabilities that persist beyond one world and transfer to later tasks. A saved memory or successful final action does not by itself establish that a reusable capability was acquired; evaluation must separate capability change from carried-over resources, unequal source exposure, and early execution failures. We construct MC-EvoBench as a controlled Minecraft benchmark with a fixed catalog of 19 registered evolution chains, including 12 primary evaluation chains and seven calibration or probe chains, together with three graph-aligned paired probe families for transfer. The benchmark represents each task as a task-state graph, defines stage-level environment verifiers, assigns matched source and target roles, resets the target world, and permits only a declared agent artifact to cross the source–target boundary. For each probe, no-prior, related, unrelated, and shuffled source conditions are evaluated under matched environment-step budgets and five seeds; we report TSR, WGP, and VMP and retain provenance records. The benchmark reveals a consistent direct-capability gap between controller and planner-backed variants, while related experience yields no stable transfer: it does not improve either tool probe, its small wood-species gain hinges on one seed, and all intervals include zero. Stage audits further show that early wood-collection and crafting bottlenecks often leave later capabilities unobserved. MC-EvoBench thus offers a controlled testbed for durable, transferable embodied capabilities. Code and data are available at https://github.com/xzw-ustc/mc-bench-open-source.
1 Introduction
One of the central ambitions of autonomous intelligence is recursive self-improvement (RSI) (Chen et al., 2026): an agent should use experience from its own actions to become more capable over time. The goal is larger than learning one policy or storing one successful trajectory. An RSI system should turn experience into a capability, retain it, and apply it when the task, world, or required action changes. This loop is central to long-horizon autonomy: as tasks become harder, the agent must build on what it has already learned.
This view differs from evaluation settings in which training is separated from testing and improvement is summarized by a single score (Ren et al., 2026). For RSI, the important question is whether a gain remains useful after the original interaction has ended. A capability should survive a change in local conditions, help with a related goal, and combine with actions that were not part of the source task. RSI is therefore a systems problem: learning, memory, planning, and physical interaction must work together, while the resulting gain remains visible and attributable.
Embodied agents make this problem concrete and difficult. Their behavior depends on both internal state and physical state. A later success may reflect a tool left in the inventory, a changed world, a favorable location, or more source interaction rather than a reusable capability. A useful benchmark must therefore show that improvement survives a reset and appears in observable behavior.
We study this question through later behavior. A memory, skill file, or model update shows that an agent changed internally. It does not show that the agent gained a useful capability (Li et al., 2025b; Park et al., 2025; Li et al., 2026). The evidence must link internal change to later action. It must also distinguish capability from favorable execution. To test that claim, we compare target behavior after a world reset and check both task outcomes and stage-level records.
Existing benchmarks address parts of this problem. MCU (Zheng et al., 2023) evaluates diverse and combined Minecraft tasks with automatic verification. LifelongAgentBench (Zheng et al., 2025), EvoAgentBench (Gao et al., 2026), and PAST-Bench (Xue et al., 2026) study learning across tasks, transfer, and persistent state in other settings. Embodied evaluation also needs to separate world resources from agent state, match source budgets, and record where a task chain fails (Ni et al., 2025; Cheng et al., 2026; Luo et al., 2025). Otherwise, a score difference may reflect an easier world, more source interaction, or an early failure that hides later behavior.
Minecraft makes these controls practical. Collecting resources, crafting tools, and using them create visible task dependencies. A task-state graph represents these relations, and environment evidence verifies each stage. Resetting the world and inventory removes physical carryover, while stage records show progress before a chain stops (Guo et al., 2025; Huang et al., 2025).
We introduce MC-EvoBench to evaluate embodied RSI in Minecraft. Figure 1 shows its mechanism: measure progress, transfer only a declared agent artifact, and use matched controls to assess experience gains. The framework can study capability formation, transfer, retention, and composition. This paper focuses on forward transfer between graph-related tasks.

Our main contributions are as follows:
- 1.
Embodied RSI as attributable capability change. We formalize an agent as a policy, a persistent state, and an update rule, and separate this persistent state from the world state. A gain counts as experience-driven only when it appears after the target world is reset, only a declared artifact crosses the source–target boundary, and matched unrelated and shuffled sources rule out alternative explanations.
- 2.
MC-EvoBench, an executable audit of experience-driven improvement. It instantiates this definition in Minecraft with a task-state graph of 80 tasks, 111 states, and 369 typed edges organized into 19 chains; stage-level verifiers with three complementary metrics, Task Success Rate (TSR), Weighted Graph Progress (WGP), and Verified Milestone Progress (VMP); and a four-condition paired protocol with matched environment-step budgets and provenance records.
- 3.
Controlled evidence on embodied transfer. Controller-based agents clearly outperform planner-backed variants in direct capability. Under matched controls, the reference method shows no stable transfer gain, even though its related sources earn more verified progress and, on the longer probes, more computation, and early wood-collection and crafting bottlenecks leave later capabilities unobserved. Future RSI methods must therefore first clear these execution bottlenecks, and their gains should be claimed only after a controlled audit.
2 Related Work
Minecraft and embodied-agent benchmarks.
Minecraft combines visual control, persistent resources, and tasks with many prerequisites. MineDojo provides a large open-world task collection and a knowledge base that supports broad embodied-agent research (Fan et al., 2022). BEDD extends MineRL (Guss et al., 2019) with demonstrations and evaluation for tasks whose success can be difficult to describe with a single exact goal. MinePlanner focuses on long-horizon planning in large Minecraft worlds, while OpenHA studies open-source hierarchical agents and their execution in the same environment (Hill et al., 2023; Wang et al., 2025). Voyager uses a curriculum, a skill library, and environment feedback for continued exploration and skill reuse, including in a new world (Wang et al., 2023). MCU evaluates a broad set of tasks, their combinations, and automatic assessment (Zheng et al., 2023). Together, these benchmarks cover open-world interaction, planning, task diversity, and automatic verification. They do not, however, isolate whether a controlled source interaction causes a later improvement after the target world is reset.
Lifelong learning and self-evolving agents.
Several recent benchmarks study improvement across tasks and the use of stored experience. LifelongAgentBench tests skill gain, retention, and transfer across databases, operating systems, and knowledge graphs (Zheng et al., 2025). EvoAgentBench uses agent traces to identify abilities and groups tasks by shared procedures, making transfer between related tasks explicit (Gao et al., 2026). PAST-Bench compares runs with and without persistent state and tracks how experience is saved and reused in personal-agent settings (Xue et al., 2026). These studies establish useful ideas for measuring persistence and transfer, but their tasks do not expose the same physical-state confounds as embodied environments. In Minecraft, an apparent gain can instead come from a carried tool, a modified world, or a different starting location. MC-EvoBench addresses this boundary by resetting inventory and world changes while allowing only a declared agent artifact to transfer. Its task-state graph makes prerequisites and progress visible.
Memory-mediated improvement and benchmark position.
Memory systems provide a practical mechanism for experience-driven improvement. Reflexion (Shinn et al., 2023) stores language feedback from failed attempts and uses it to guide later decisions. Agent Workflow Memory extracts reusable procedures from interaction traces for later tasks (Wang et al., 2026). Skill libraries and model updates offer related ways to preserve information beyond a single episode. These methods show how an agent can store and retrieve experience, but reuse alone does not establish that a capability transferred. MC-EvoBench treats experience-driven improvement as an attribution problem. It separates source and target episodes, resets the physical state, and transfers only a declared artifact. Matched source conditions, verifier predicates, and stage records distinguish capability transfer from carried-over resources and partial execution.
3 MC-EvoBench Framework and Benchmark Design
MC-EvoBench tests whether experience changes later behavior. To support that claim, it resets the target world, checks outcomes against environment evidence, and compares matched source conditions. Figure 2 shows how these parts work together. Panel (a) follows the agent from source interaction to target evaluation. Panel (b) shows the tasks, states, relations, chains, and environment profiles that define each test.
3.1 Evaluation Target and State Boundary
We ask whether controlled source interaction improves performance on a later target task in a reset world. A stored memory or model update cannot answer this question by itself. We represent an agent as \(A=(\pi,z,U)\): \(\pi\) selects actions from observations and goals, \(z\) is the state the method can retain, and \(U\) updates that state from experience. Source experience \(E_{S}\) produces \(z_{S}=U(z_{0},E_{S})\). The evaluator records and freezes \(z_{S}\) before the target run. No source resources, positions, world edits, route information, or success markers enter the target.
World state includes inventory, tools, resources, position, terrain, and world changes. Persistent agent state may include memories, prompts, replay data, checkpoints, or model updates. Every target run starts with the same registered world and inventory settings. Thus, source tools and world changes cannot explain a target score difference. A stored artifact provides evidence of a gain only when the target verifier also records a change in behavior.
3.2 Task-State Graph
MC-EvoBench represents task dependencies and observable resource flow with
|  | \[G=(\mathcal{T},\mathcal{S},\mathcal{E}),\] |  |
Here, \(\mathcal{T}\) contains tasks, \(\mathcal{S}\) contains observable states, and \(\mathcal{E}\) contains typed relations. States include items, tools, locations, structures, and task completion. The graph describes what tasks require, produce, or consume without prescribing an action sequence. These three relation types form the strict execution graph. The remaining types, enables and abstracts_to, describe possible capability links and task categories; neither proves transfer. Appendix B.2 defines each edge type and gives their counts.
Tasks form stage chains \(C=(\tau_{1},\ldots,\tau_{K})\). Each stage has a goal that the verifier checks against run evidence. The chain shows prerequisites and where execution stops; the agent remains free to choose its actions. Stage records reveal partial progress even when the final goal is not reached. Catalog and probe chains use the same task definitions and verifier rules. Reset settings, retained state, and step budgets are fixed before evaluation.
3.3 Paired Protocol and Metrics
Each comparison has a source phase and a target phase. The source agent interacts with registered tasks and forms \(z_{S}\). The evaluator then resets the target world and inventory, freezes \(z_{S}\), and runs the target task with the same verifier. Four target conditions serve different purposes. No-prior provides a baseline; related experience tests for a change; unrelated experience tests whether that change depends on task relevance; and shuffled related experience tests whether task order matters. We record source steps, termination, artifact identity, and target outcomes. Source episodes restart after early termination until the declared budget is used.
The verifier records the evidence for each stage, changes in resources, pass status, and why the run stopped. Let \(v_{i}\) indicate whether stage \(i\) passes. For each strict execution edge \(e\), \(w_{e}\) is its weight and \(q_{e}\) indicates verified progress. Let \(m_{j}\) indicate whether eligible milestone \(j\) is reached. The three direct metrics are
|  | \(\displaystyle\mathrm{TSR}\) | \(\displaystyle=\frac{\sum_{i=1}^{K}v_{i}}{K},\) |  | (1) |
|  | \(\displaystyle\mathrm{WGP}\) | \(\displaystyle=\frac{\sum_{e\in E_{\mathrm{exec}}}w_{e}q_{e}}{\sum_{e\in E_{\mathrm{exec}}}w_{e}},\) |  | (2) |
|  | \(\displaystyle\mathrm{VMP}\) | \(\displaystyle=\frac{\sum_{j=1}^{J}m_{j}}{J}.\) |  | (3) |
TSR is the fraction of planned stages that pass; unreached stages remain in its denominator. WGP is the weighted fraction of strict graph edges supported by verified progress. VMP tracks eligible item or tool milestones observed before a chain ends. It captures partial progress, not full completion. We report all three metrics for each target condition and compare paired runs. Appendices C and D.6 give the verifier and reporting rules.
3.4 Benchmark Instantiation
MC-EvoBench implements this framework in Minecraft with a fixed task catalog, verifiers, probe profiles, and observation interface. A change to any of these components defines a new benchmark version. The same evaluation can therefore test different ways of storing experience, such as textual memories, skill libraries, prompts, or model updates, under a shared task and evidence specification.

3.4.1 Frozen Catalog and Probe Families
The catalog contains 80 tasks, 111 state nodes, 369 graph edges, 19 registered chains, 12 general profiles, and 3 paired-transfer profiles. Its 19 chains include 12 primary evaluation chains and 7 calibration or probe chains. Tasks span building, survival, exploration, and combat. Long chains test execution across many prerequisites. Short probes test local transfer that an early failure in a long chain could hide. The probes use catalog tasks and the same verifier rules. Appendices F and A.3 list the tasks, chains, and profiles.
The three probe families and their budgets are listed in Table D.3 of Appendix D.3. In each family, related and target chains share a dependency pattern but end with a different object or tool. This lets us test transfer while keeping the required preparation steps. Each stage has a 450-step cap. After early termination, a new episode starts until the family budget is used.
3.4.2 Environment and Observation Interface
Paired-transfer runs use public world seed 31, an empty target inventory, and one of three fixed environment profiles (Appendix A.3); direct-capability runs use the seeds and per-stage profiles in Table F.3. Profiles set time, weather, spawn, clearance, and public resources. They do not provide target items, routes, private coordinates, or verifier state. The agent must observe and collect resources through interaction. Each target condition starts with a world and inventory reset; only the declared agent artifact can transfer. The agent sees normal observations, while the graph, verifier rules, diagnostics, and hidden coordinates remain unavailable. Appendices A.2 and C.1 detail these access rules and verifier checks.

4.1 Evaluation Setup
The paired evaluation uses three probe families: wood-species crafting, wooden-tool transfer, and stone-tool transfer. Each family uses five paired agent seeds and four target conditions: no prior, related experience, unrelated experience, and shuffled related experience. Every target starts from the same world and inventory state for its family. Only the declared agent artifact may cross the source–target boundary. We report TSR, WGP, and VMP as defined in Section 3.3. Source exposure is matched within each family; planner calls and token usage are recorded separately because equal environment exposure does not imply equal computation.
4.2 Direct Capability Matrix
The direct matrix covers 12 primary evaluation chains (five core-progression, four catalog-transfer, and three diversity) and nine direct configurations, each evaluated with three seeds. Each cell in Table 2 averages TSR / WGP / VMP over the chains in a partition; the final columns weight the partitions by their sizes (5/4/3), and Appendix Table F.3 gives per-chain scores. These runs measure direct capability rather than transfer; ExpeL (Zhao et al., 2024) has one separately marked report per chain and is excluded from these aggregates.
Controller-based execution clearly outperforms planner-backed execution. STEVE-1 (Lifshitz et al., 2023) and the controller-only JARVIS-1 (Wang et al., 2024) and Optimus-1 (Li et al., 2024) variants reach average TSR/WGP/VMP of 8.4/6.4/25.5, 7.5/5.5/25.0, and 8.1/6.1/25.4, with the largest margins on the core and catalog-transfer partitions, where progress requires several dependent actions. The no-op baseline and the GPT-planned JARVIS-1 remain at the execution floor, confirming that the benchmark separates active task solving from background behavior. No planner dominates all three metrics: DeepSeek gives the highest average TSR for both JARVIS-1 (2.8) and Optimus-1 (4.9), whereas the highest VMP comes from DeepSeek for JARVIS-1 (6.0) but from GLM for Optimus-1 (12.5). The official VPT (Baker et al., 2022) foundation weights improve over the STEVE-1 checkpoint (average VMP 10.4 versus 3.2) but remain below the controller variants.
4.3 Paired Transfer Results
Table 3 reports mean target scores in the order no-prior / related / unrelated / shuffled. The study contains 105 source and target role reports in total, with 60 target reports contributing to the four-condition comparison.
For wood-species crafting, related experience gives scores close to no prior. The shuffled control scores at least as high on TSR and WGP. For wooden-tool and stone-tool transfer, related experience scores below no prior on all three metrics. On the stone-tool probe, related TSR, WGP, and VMP are 0.050, 0.021, and 0.200, compared with 0.150, 0.082, and 0.533 for no prior.

4.6 Failure Stages, Seed Variation, and Scope
In the failure-stage audit of the 57 direct-matrix reports per configuration (Figure 3a), attrition concentrates in the first crafting steps: of the 42 reports that include wood collection, the three controller variants bring 20–23 to plank crafting, at most 14 to sticks, and at most 2 to the crafting table, while the Optimus-3 (Li et al., 2025a) action path never passes the initial wood stage. A low final score can therefore reflect an early execution bottleneck rather than the failure of a later capability, which remains unobserved. Per-seed effects (Figure 3b–c) vary most for wood species, where the small positive mean GATG (\(+0.050\)) is driven by a single seed (\(+1.0\)) and falls to \(-0.19\) without it; the tool probes vary less and have GATG means near zero. All three intervals cross zero, consistent with Table 4.
Taken together, the direct matrix measures immediate capability rather than transfer, and the paired probes should be read against its low execution floor. Under the current public instances, seeds, budgets, and reference method, related experience does not produce a stable positive transfer effect; this does not rule out gains under a different agent, artifact, task distribution, or source budget. Appendices C.3, D.6, and E.4 give the stage records, paired-reporting rules, and configuration fields needed to reproduce these comparisons.
5 Conclusion
We introduced MC-EvoBench, a controlled Minecraft benchmark for auditing whether experience yields durable and transferable embodied capabilities. Its task-state graph, stage-level verifiers, and paired reset-target protocol with matched control sources separate capability change from carried-over resources, unequal exposure, and early execution failures. In the reference study, controller-based agents clearly outperform planner-backed variants, yet the reference method gains no stable target benefit from related experience: the only positive contrast, on wood species, is driven by a single seed, and all intervals include zero even though related sources earn more verified progress and, on the longer probes, more computation. Most runs also end before crafting sticks, leaving later capabilities unobserved. These conclusions are limited to the tested agents, probes, seeds, and budgets; retention, composition, stronger agents, and more seeds are natural next steps.

Ethics statement
This work evaluates agents in a virtual Minecraft environment. It does not involve human participants, personal data, or physical-world experiments. We use environment states and agent interaction traces to measure task execution and experience transfer. Any released code, task definitions, assets, and logs will follow their applicable licenses and include documentation for reproduction. The results apply to the tested methods, tasks, environments, and budgets. They do not establish that these agents are safe or capable in real-world settings.

Appendix A Minecraft Environment Settings
MC-EvoBench evaluates whether interaction experience can improve subsequent embodied execution. Its experimental unit joins a source experience, a persistent agent artifact, and a separately initialized target evaluation. This appendix specifies the environment, task construction, verification, experimental protocol, agent interfaces, task suite, and reproducibility materials.
A.1 Game world and interaction interface
The primary environment is Minecraft 1.16.5 through MineRL, with a custom survival specification named MCBenchHumanSurvival-v0. It extends the HumanSurvival environment with observations for inventory, local resources, world conditions, and task events. The agent interacts with the game through an adapter, while a separate evaluator converts the environment response into a normalized observation snapshot. This separation supports a common task definition across agents with different planning and control architectures.
The native control interface consists of movement, camera rotation, attack, use, and inventory operations. Camera commands change pitch and yaw; the meaning of attack and use depends on whether the agent is interacting with the world or an inventory interface. These environment actions produce the observations used for task verification. Text-conditioned controllers translate a task instruction into this action interface. A programmatic agent may use a different bridge, in which case its action granularity is reported with the method settings in Appendix E.

| Component | Representation | Role |
|---|---|---|
| Visual input | First-person RGB frame | Scene perception and low-level control |
| Movement | Forward, back, left, right; jump, sneak, sprint | Navigation and locomotion |
| Camera | Relative pitch and yaw | Viewpoint and interaction targeting |
| Interaction | Attack, use, drop, inventory, hotbar selection | Resource collection, construction, and item manipulation |
| Inventory and equipment | Item counts; normalized equipped-item names | Agent context when exposed; task verification |
| Local resource evidence | Ray observation and block-count grid | Structured perception or evaluator evidence, according to the adapter |

A.2 Observation access and normalized evidence
The catalog distinguishes native_perception and structured_state observation sources. Each source records a path, its primary or diagnostic role, its interpretation, and an access declaration. Inventory, equipment, and basic survival measurements are examples of declared agent-visible sources. Local block counts, mission flags, kill counters, and world-light diagnostics are classified as structured evidence. RGB-based and structured-state methods therefore remain distinguishable even when they share the same task verifier.
At runtime, the snapshot groups observations into inventory, equipment, player statistics, counters, flags, raw observations, and environment metadata. Equipment names are normalized across MineRL representations, and raw entity-kill observations can populate the corresponding normalized counter. The evaluator preserves the raw channel alongside the normalized value, which makes it possible to trace a predicate back to its observation source. The actual model inputs are determined by the adapter; Appendix E describes the built-in interfaces.
The local block grid spans offsets from \((-3,-2,-3)\) to \((3,2,3)\) around the player, giving a \(7\times 5\times 7\) observation volume. The ray channel supplies a block identity and distance. Grid counts support local structure checks; ray observations support direct resource visibility. Profile-provided resource markers describe the configured scene and serve as diagnostics. The coal-discovery predicate uses coal observed in the ray channel or local block grid.

A.4 State continuity within a task chain
The chain specification selects either a task-level or chain-level profile policy. Under the task-level policy, the runner selects each task’s profile; with the default per-stage reset setting, a profile change causes an environment reset. Under the chain-level policy, one selected profile governs the chain. Consecutive stages that remain in the same environment can reuse world resources and inventory, making state continuity an explicit part of chain evaluation.
This within-chain continuity is separate from the source-to-target boundary. A target transfer evaluation starts from its prescribed environment state and receives only the permitted persistent artifact. A tool retained between two stages changes their execution conditions; a tool reconstructed after a target reset provides evidence about execution under the retained agent state. The protocol records these two situations separately.
Appendix B Task Construction and Composition
B.1 Task specification and benchmark coverage
A task is a compact executable contract: an identifier, an instruction, a domain, a step budget, an environment profile, a success specification, and observation-source declarations. Instructions describe ordinary Minecraft objectives such as collecting a resource or crafting a tool. The success specification supplies the measurable endpoint. Keeping these fields together allows the same task to be placed in a short probe, a longer chain, or an independent evaluation without redefining its meaning.
The task catalog contains 80 tasks across building, survival, exploration, and combat. The domain counts are 40, 26, 7, and 7, respectively. The accompanying graph contains 111 state nodes and 369 edges. Its composition rules connect resource acquisition, crafting, tool use, environmental conditions, and high-level events. Appendix F provides the complete task and chain definitions; the machine-readable tables retain the original instructions and predicates.
Table B1. Catalog partitions and their execution denominators. A task identifier can occur more than once in a chain or across chains. Stage occurrences are therefore counted separately from distinct task membership.
| Partition | Declared tasks | Chains | Stage occurrences | Purpose |
|---|---|---|---|---|
| Core progression | 33 | 5 | 71 | Resource, tool-tier, survival, and combat progression |
| Transfer | 31 | 4 | 50 | Item, recipe, and schema substitutions |
| Supplementary diversity | 16 | 3 | 19 | Breadth of collection and resource interaction |
| Calibration and probe | 0 | 7 | 51 | Execution and verifier checks |
| Primary evaluation total | 80 | 12 | 140 | Core, transfer, and diversity combined |
The first three partitions define the primary evaluation suite. The calibration partition reuses task definitions for engineering checks and is reported separately. This organization supplies both a stable comparison set and a small set of diagnostic entry points. The task-membership split describes the catalog taxonomy; shared prerequisites can still recur in the executable chains.

B.3 Ordered chain compilation
A chain stores an ordered task sequence, initial symbolic states, an environment profile, and a profile policy. The compiler traverses the sequence and extracts five paths for every occurrence: hard prerequisites, produced resources, consumed resources, soft enabling relations, and abstraction relations. Repeated task identifiers become distinct compiled stages, so their positions and local context remain available to the evaluator.
The default compiler checks prerequisite presence in the evolving symbolic state set. An optional strict-quantity mode also checks declared resource counts before consuming and producing them. Let \(q_{j}(s)\) be the symbolic availability of state \(s\) before stage \(j\). In the strict mode, a stage requires sufficient declared counts, after which its resource bookkeeping follows
|  | \[q_{j+1}(s)=q_{j}(s)-c_{j}(s)+p_{j}(s),\] |  | (B.2) |
where \(c_{j}\) and \(p_{j}\) are the stage’s consumption and production counts. Initial symbolic states seed this calculation; they do not grant physical inventory. The simulator independently realizes movement, mining, crafting, and resource use.
This separation is useful when constructing a benchmark: a chain can be checked for intended ordering before a game is launched, and its execution can then be evaluated from observations. Equation B.2 describes symbolic bookkeeping only. The compilerś output also gives each stage a fixed metric context, with graph weights fixed by the planned chain before execution.
B.4 Composition patterns
Resource progression chains connect acquisition to increasingly demanding use. For example, the ore progression chain moves through wood preparation, basic tools, stone tools, ore collection, smelting, and higher-tier mining. Cross-domain chains join heterogeneous endpoints: locating coal, obtaining fuel, creating illumination, building shelter, and remaining alive, or preparing a weapon before a combat event. Transfer chains substitute wood species, tool recipes, or item roles while retaining comparable dependency patterns.
The task suite also includes short probes. These isolate resource collection or limited crafting sequences, helping distinguish an early execution bottleneck from a long-horizon planning requirement. A short probe and a long chain answer different questions, even when they contain the same task identifier. Their sequence, start state, budget, and profile policy accompany their scores.
A completed possession task establishes its predicate at that stage. If the same item remains in inventory, a later occurrence with the same predicate may pass immediately. The ordered stage record makes this behavior explicit: initial-state passes have zero action steps, while newly acquired items appear in the observed state transition. Composition is consequently described through stage outcomes and state continuity, with experience transfer assessed by the reset protocol in Appendix D.
B.5 Extending the catalog
A new task can be added by defining its instruction and measurable endpoint, identifying the required observation channels, selecting an environment profile, and attaching its graph relations. A new chain then specifies an ordered list of existing or new task identifiers. Compilation checks the declared dependency order, and an execution check verifies that the configured environment exposes the evidence required by its predicates.
The reusable components are the task contract, graph relations, profile registry, and runner interface. A method’s planner, retrieval rule, or memory format remains outside the task definition. This allows a future agent to implement a different experience representation while being evaluated against the same target objectives and evidence rules.
Appendix C Success Verification and Execution Metrics
C.1 Predicate-based task evaluation
MC-EvoBench evaluates success from environment observations. A task contains a conjunction of predicates, with optional disjunctive subexpressions. Inventory thresholds check resource or item possession; equipment predicates accept an item in a specified slot; counters capture events such as an entity defeat; snapshot comparisons read a named observation field. These primitives cover both simple item goals and objectives that combine player state with local environmental conditions.
Table C1. Supported predicate families and their measurement roles.
| Predicate family | Accepted evidence | Example |
|---|---|---|
| Inventory threshold | Named item count at or above a threshold | At least four oak planks |
| Equipment equality | Normalized item in the specified equipment slot | Stone sword in the main hand |
| Counter threshold | Observed event count | At least one zombie defeated |
| Player-stat threshold | Named player measurement | Positive life or health |
| Snapshot comparison | Named path, comparison operator, and value | Observed coal-ore indicator at least one |
| Flag membership | Flag produced by the configured event logic | A mission state supported by its observation rule |
| Disjunction | At least one successful child predicate | Item in inventory or equipped |
A snapshot-path comparison fails when its required path is absent. Inventory and counter thresholds use zero for a missing count. The diagnostic record stores the predicate and its observed value, making the distinction between a satisfied condition and unavailable supporting evidence inspectable. Item possession is measured directly from environment observations.
The evaluator checks the initial snapshot before requesting an action. If all predicates already hold, the stage passes with zero steps. Otherwise, it checks after each environment transition until success, a mission failure, environment termination, or budget exhaustion. A stage limit is the smaller of its catalog budget and any configured cap. The normal chain runner stops at the first non-passing stage, preserving the distinction between the observed prefix and unattempted suffix.
C.2 Mission events
Four mission-event definitions extend the basic predicates with observation-derived conditions. Their triggers combine local perception, lighting, elapsed time, and entity events. Event evaluation can attach a normalized flag or counter to the snapshot, after which the ordinary task verifier reads the corresponding evidence. This approach keeps event semantics shared between the runner and the task specification.
Table C2. Mission-event rules. Thresholds are taken from the catalog. The shelter rule is a local structure-and-light criterion; the night rule measures a defined survival interval.
| Event | Trigger | Endpoint |
|---|---|---|
| Coal source observed | Coal ore appears in the ray channel or local block grid | Observed resource discovery |
| Lit shelter observed | At least one local torch; at least 60 non-air blocks; effective light at least 7; sky light at most 7 or sky blocked | Local sheltered and lit condition |
| Night interval survived | Player alive; elapsed time at least 1,800 ticks; final time in the night window from 12,000 to 24,000 | Survival over the configured interval |
| Zombie defeat observed | Normalized zombie counter or raw zombie-kill count at least one | Observed combat event |
For survive_first_night, the runner also derives night_survived from player survival and elapsed time reaching the effective stage limit. This additional path uses the total-time difference when available; its world-time fallback also requires a night endpoint. Thus the effective interval follows a configured stage cap, while Table C.2 specifies the catalog event rule. Survival, shelter, and combat events include a player-death failure condition. Event records preserve the evidence that caused a terminal decision, so later analysis can connect a stage outcome to the underlying world measurement.
C.3 Stage records and evidence organization
Each stage record identifies the task occurrence, terminal status, action-step count, and failed predicates. Its diagnostics include start and final snapshots, declared observation sources, actual predicate values, mission evidence, and the compiled graph paths. The chain report retains the planned stage count and planned graph weight even when execution stops early.
Table C3. Terminal statuses and their interpretation in chain aggregation.
| Status | Interpretation | Contribution to passed-stage numerator |
|---|---|---|
| passed | All success predicates hold | One |
| failed | A configured mission failure is observed | Zero |
| terminated | The environment ends before success | Zero |
| timeout | The effective stage limit is exhausted | Zero |
| budget_exhausted | A smaller remaining chain/source budget is exhausted | Zero |
| Unattempted suffix | Earlier stopping prevents execution | Zero, with missing execution recorded separately |
This record supports analysis at several resolutions. A chain score summarizes completed requirements; stage records locate its execution breakpoint; start and final states describe resource changes; and optional action traces support a finer behavioral account. These resolutions share the same task identity and sequence position.
C.4 Task success rate and weighted graph progress
For chain \(c\), let \(L_{c}\) be its number of planned stage occurrences and \(y_{cj}\) indicate whether occurrence \(j\) passes. Task success rate is
|  | \[\mathrm{TSR}=\frac{1}{L_{c}}\sum_{j=1}^{L_{c}}y_{cj}.\] |  | (C.1) |
In Eq. C.1, unattempted stages remain in the planned denominator. At split level, the aggregate pools passed occurrences and planned occurrences across the included chains. This weights every planned occurrence equally, while completed-chain counts offer a complementary measure of end-to-end execution.
For chain \(c\), let \(E_{\mathrm{exec},c}\) be its strict execution edges, formed by the requires, produces, and consumes relations. Let \(w_{e}\) be the edge weight and \(q_{e}\) indicate whether the corresponding verified stage contributes. Edge weights default to one when unspecified. Weighted graph progress is
|  | \[\mathrm{WGP}=\frac{\sum_{e\in E_{\mathrm{exec},c}}w_{e}q_{e}}{\sum_{e\in E_{\mathrm{exec},c}}w_{e}}.\] |  | (C.2) |
In Eq. C.2, an edge is credited when its corresponding verified stage contributes. Shared resources can appear in several stage paths, and each occurrence contributes its local edge weight. Split WGP pools completed and planned edge weights across chains. A chain with no planned execution-edge weight falls back to TSR. Together, TSR and WGP summarize stage completion and its execution structure using fixed planned denominators.
C.5 Milestone and efficiency diagnostics
Verified milestone progress (VMP) describes observed acquisition of graph-linked items or tools. For each reported stage, the metric extracts item/tool states from its execution paths and assigns each state the largest included edge-count threshold. A state is eligible if the first recorded snapshot is below its threshold; it is credited if a later recorded stage-start or stage-final snapshot reaches the threshold. The score is
|  | \[\mathrm{VMP}=\frac{\text{eligible states reaching their thresholds}}{\text{eligible states}},\] |  | (C.3) |
Equation C.3 returns zero when the eligible set is empty. The associated eligible count is part of its interpretation. Because this set follows the reported prefix, VMP is used as a local acquisition diagnostic alongside the fixed-denominator TSR and WGP endpoints. A task passes when its success predicates hold.
Efficiency summaries include environment steps, stage budgets, steps per passed stage, and observed deaths. Resource-use diagnostics identify consumed items whose inventory decreases during a non-passing stage. This provides a traceable signal of material expenditure associated with unsuccessful execution. Recovery events require an explicit adapter record and can then be aligned with stage transitions.
C.6 Verification examples
The task craft_planks requires at least four oak planks. The objective is therefore satisfied by the corresponding inventory count. For craft_stone_sword, the catalog accepts a stone sword either in inventory or in the main hand, matching the game’s distinction between carrying and equipping a tool. The coal-discovery task uses observed coal in a ray or grid channel; the subsequent coal-collection task checks the collected item.
These examples illustrate why the task contract separates an instruction, its observation sources, and its terminal predicate. The instruction gives the agent a goal, the observation contract defines the evidence channels, and the predicate fixes the endpoint. The same decomposition supports independently checking an item goal, a temporal objective, or a cross-domain chain through explicit predicates.
Appendix D Evaluation protocol
D.1 Experience, artifact, and target evaluation
MC-EvoBench separates capability measurement from the experience that may change an agent. A paired evaluation first measures a target with the base agent, then measures the same target with an artifact produced through a specified source curriculum. The artifact may contain updated parameters, memory, a skill library, or another declared persistent representation. Its identity and provenance define the agent state being evaluated. This interface accommodates different adaptation mechanisms while keeping the target task and its verifier fixed.
At the source-to-target boundary, the target world and inventory are reset. Only the frozen method-produced artifact crosses this boundary. Consequently, tools, blocks, completed constructions, and resource inventories accumulated during source interaction do not supply target progress. In the supplied memory configuration, source interaction uses read_write memory and target evaluation uses read_only memory. Each target role constructs a fresh agent and environment; persistent source experience is loaded from its declared artifact.
Within a compiled chain, stages execute in order and preserve the environment state permitted by the chain profile. The runner stops at the first non-passing stage. The transfer probes use one chain-level profile throughout an episode. Source episodes can restart to complete their interaction budget, as described in Appendix D.3. These distinct boundaries preserve sequential task dependencies within an episode and isolate learned experience across evaluations.
Figure D1. Each source condition produces its own artifact from the same base agent. Target evaluations share task, world, budget, and seed settings. At the boundary, the world, inventory, and transient agent state are reset while the declared persistent artifact is retained.
D.2 Paired target roles and controls
Each probe and replicate defines three source roles and four target roles. All four target roles use the same target task sequence, verifier, environment profile, world seed, stage limits, and agent seed. They differ in the artifact supplied to the agent.
Table D1. Target roles and the question addressed by each source condition.
| Target role | Artifact supplied | Comparison supported |
|---|---|---|
| No prior | Base artifact without the evaluated source experience | Initial target capability |
| Related | Artifact after graph-related source tasks | Transfer from relevant experience |
| Unrelated | Artifact after unrelated source tasks | Effect of generic extra experience |
| Shuffled | Artifact after the related task multiset in reversed order | Sensitivity to source ordering |
The unrelated and shuffled source conditions receive the same family-level environment-step budget as the related condition. The shuffled source uses the identical task multiset, including repeated tasks. Its probe explicitly allows compilation with unmet prerequisites, making the reversed sequence executable without adding inventory or changing success predicates. Normal runtime stopping rules still apply, so the resulting experience can include repeated unsuccessful episodes.
The target input contract provides the natural-language instruction and agent observation, together with the declared artifact. It reserves graph-relation manifests, verifier predicates, verifier diagnostics, and hidden resource coordinates for evaluation. The built-in method inputs are detailed in Appendix E. Public resource placement defines the controlled task instance. It does not supply target inventory items, forced success evidence, private route hints, or scripted actions.
D.3 Frozen transfer probes and source exposure
The protocol provides three shorter graph-chain families assembled from catalog tasks. Shorter targets make transfer at intermediate capabilities observable even when a long progression chain stops at an early prerequisite. The plan freezes task sequences, resource profiles, source–target relations, and budgets before adaptive paired evaluation.
Table D2. Transfer probe families. Source exposure is matched within each row; the target sequence is held fixed across artifact conditions.
| Probe family | Related source \(\rightarrow\) target variation | Stages per sequence | Source steps per condition |
|---|---|---|---|
| Wood species | Birch logs and planks \(\rightarrow\) acacia logs and planks | 2 | 900 |
| Wooden tools | Wood preparation and wooden axe \(\rightarrow\) wooden shovel | 5 | 2,250 |
| Stone tools | Wood/stone preparation and stone pickaxe \(\rightarrow\) stone shovel | 8 | 3,600 |
The wooden-tool pair shares the log, plank, stick, and crafting-table preparation sequence. The stone-tool pair additionally shares wooden-pickaxe preparation and two cobblestone-mining stages. Unrelated source sequences contain the same number of stages and use collection tasks outside the selected production chain. The resource profiles provide local world resources while retaining the need to acquire and transform them through agent interaction.
The probe configuration imposes a 450-step ceiling on each stage, retaining a lower catalog limit if one exists. The fixed-exposure source runner is enabled by experiment.source_interaction_budget_steps. Source exposure is measured as actual environment interactions. If a source episode ends before its family budget is consumed, the agent receives normal terminal feedback, the source environment resets, and interaction resumes with the persistent method artifact. The last episode is truncated at the remaining budget. Thus early completion or failure changes the number of episodes without reducing the prescribed source exposure. The source report records every episode and the total interaction count; a final paired comparison requires all three source conditions to consume the common budget.
D.4 Replicates and reproducibility
The headline paired protocol uses five final agent seeds, 5100–5104. Separate calibration checks may use at least three direct seeds, but they are not part of the 105 role configurations or the headline results. The replicate axis is agent randomness on a fixed controlled world: the public world seed is 31. Fixing the world preserves the declared spawn placement and local resource layout across conditions. The resulting paired estimates characterize variation across agent seeds on these controlled instances.
Run labels such as seed0 identify records; numerical world_seed and agent_seed fields determine randomization. The runner applies the world seed to the environment and seeds Python, NumPy, and PyTorch before constructing the policy. Reports retain both seeds and their provenance. Every role in a paired replicate uses the same numerical seeds, and the same replicate list is used across conditions.
Before rollout, the launcher checks the declared resource profile through an environment reset. Artifact manifests record identities and paths, with SHA-256 fingerprints available for files and directory bundles. Together, the frozen plan, explicit seeds, artifact identity, and runtime configuration specify a reproducible comparison.
D.5 Transfer contrasts
TSR, WGP, and VMP follow the definitions in Appendix C. Let \(M_{0},M_{R},M_{U},M_{S}\) denote a target score with no prior, related, unrelated, and shuffled artifacts, respectively. Define each source condition’s change from the no-prior target as
|  | \[\Delta_{c}=M_{c}-M_{0},\qquad c\in\{R,U,S\}.\] |  | (D.1) |
The paired differences in Eq. D.1 are interpreted across the three direct metrics. A related-source change is compared with both the no-prior baseline and the matched unrelated and shuffled controls; these are contrasts over TSR, WGP, and VMP rather than additional benchmark metrics. Target TSR is the primary channel, while WGP and VMP provide complementary completion and acquisition diagnostics.
D.6 Statistical and diagnostic reporting
Compute contrasts within each matched replicate before summarizing across seeds. Report the four target scores and paired differences for each direct metric, with their means and sample standard deviations. The aggregation helper also computes two-sided 95% Student-t intervals on paired seed contrasts:
|  | \[\bar{d}\ \pm\ t_{0.975,n-1}\frac{s_{d}}{\sqrt{n}}.\] |  | (D.2) |
For the interval in Eq. D.2, \(n\) is the number of valid pairs and \(s_{d}\) is the sample standard deviation of paired differences. A beneficial-transfer interpretation requires a positive related-source change relative to the no-prior baseline and matched controls, supported by paired uncertainty. Metric configurations are also characterized as floor-limited, ceiling-limited, or interior. The accompanying progress channels localize capability acquisition across these score regimes.
Report environment steps alongside source episode counts, outcomes, memory updates, planner calls, and token usage. Equal environment exposure can produce different amounts of planning and updating because episodes terminate at different points. These diagnostics characterize the resources used to create each artifact and support computation-aware comparisons. Per-seed target scores and source exposure remain available alongside aggregate statistics, allowing transfer and efficiency to be assessed together.

Appendix E Agent implementations
E.1 Observation and action interfaces
MC-EvoBench connects policies to a common chain runner through a policy factory, a reset operation, and an action function. At each interaction, the adapter supplies the task instruction and current observation and receives a MineRL action mapping. The default prompt template is the instruction itself. Optional callbacks provide stage status and the number of executed steps, allowing methods with persistent memory to update after source experience. Table E.1 specifies the implemented method variants and their effective inputs; these interfaces define the observation, action, and persistent-state conditions used in each comparison. The table documents supported adapters; the headline reference study reported in the main paper uses only the JARVIS-1 online extension, while the other entries do not contribute to the paired-transfer results.

VPT loads its network specification and policy-head settings from the model file; its sampling temperature is inherited from that file. Optimus-3 creates a task representation when the instruction changes, then combines it with successive frames.
E.2 Persistent experience and adaptation
The JARVIS online extension stores stage-level textual records containing the instruction, proposed plan, dispatched controller prompts, status, interaction count and visible-state summary. Retrieval uses token-set Jaccard similarity between the current instruction and each stored instruction, adds 0.15 for a successful record, and breaks score ties in favour of newer records. Up to four positive-scoring records condition planning. Memory retains the latest 256 records and is written atomically. The planner returns one to six short controller prompts; reflection produces a practical sentence capped at 500 characters. The reflection input distinguishes a proposed plan from prompts actually dispatched and labels the state summary as the last pre-action observation.
ExpeL uses the same episode-retrieval score and supplements episodes with retrieved textual insights and a weighted rule list. Insight retrieval uses lexical overlap; rule retrieval adds a weight contribution capped at 0.10. With the configured insight limit of eight, the planner may receive up to eight insights and eight rules. Reflection proposes ADD, EDIT, REMOVE and AGREE operations. New rules start with weight two; agreement and editing increment weight, while removal decrements it. The persistent artifact records these updates alongside episode actions. Both memory methods support read-write source interaction and read-only target evaluation; read-only stage callbacks suppress reflection and memory writes.
E.3 Planning and execution cadence
The JARVIS extension plans when a new stage instruction becomes active. It dispatches successive subgoals for fixed 120-step intervals and retains the final subgoal for any remaining stage steps. Stage completion invalidates the active instruction so repeated task text can trigger a new plan. Optimus-1’s visual planner uses the same interval rule and a JSON subgoal format. Its input is a JPEG thumbnail bounded by 384 \(\times\) 384 pixels at quality 85. The parser filters subgoals containing “open,” “place,” or “access” followed by a space, rewrites punch/collect/gather to chop, and retains up to six subgoals. ExpeL instead requests a low-level action mapping and can hold that action across a configured number of environment steps. The 19-chain configuration sets this hold to 32, while the factory default is one. Its prompt also supplies explicit line-of-sight guidance for approaching and mining visible resources.
The Voyager skill bridge follows a separate execution protocol. The runner loads released JavaScript skills and control primitives, resets through the Mineflayer bridge with empty inventory and equipment, and invokes a fixed skill sequence. A configured starting position is applied during setup. The runner checks the returned inventory for its designated target item. Its step count denotes a bridge request, and the implementation invokes no LLM; this execution unit is recorded separately from MineRL interaction steps.

Appendix G Prompts and Reproducibility
G.1 Planning and reflection templates
The online-memory reference implementation uses two system templates. The planning request combines the current goal, an agent-visible state summary, and retrieved experience. It returns a small sequence of text subgoals for the visual controller. The reflection request summarizes a completed source episode for later retrieval. Cards G.1 and G.1 specify the input–output contracts and system prompts.
The planning payload contains goal, visible_state, and retrieved_experience. Retrieved records expose the instruction, plan, status, and advice. The planning parser returns up to six non-empty steps, using the task instruction as its default. Reflection receives stage feedback together with the actually dispatched prompts, allowing the stored advice to distinguish planned behavior from observed execution context.
G.2 Persistent memory representation
The artifact is a JSON object containing a record count and a list of episode records. Each record associates a task instruction with a proposed plan, the prompts dispatched to the controller, terminal status, interaction count, visible state, and advice. The memory writer keeps the latest configured number of records and replaces the artifact atomically. Retrieval and update rules are specified in Appendix E; the schema below describes the fields required to inspect the stored experience.
Table G1. Persistent memory fields and their interpretation.
| Field | Content | Role in reproduction |
|---|---|---|
| format | Memory schema identifier | Identifies the memory format |
| record_count | Number of retained records | Checks artifact size |
| instruction | Task text | Retrieval key |
| plan | Proposed controller prompts | Records planner output |
| dispatched_plan | Prompts actually sent to the controller | Links planning to dispatch |
| status, steps | Stage outcome and executed steps | Captures feedback supplied to the method |
| visible_state | Agent-side state summary | Records the reflection context |
| advice | Concise text retained for reuse | Reusable experience content |
The source artifact is copied or otherwise identified before target evaluation, and its fingerprint accompanies the target role. Read-only target memory keeps the supplied experience fixed throughout evaluation. This makes the artifact itself an inspectable component of a paired comparison.
G.3 ExpeL action and rule templates
The ExpeL adaptation uses separate system templates for selecting an environment action and extracting reusable experience. Cards G.3 and G.3 specify the action and reflection interfaces. The action payload contains instruction, observation, experiences, and insights. The final field combines insight text with retrieved rules formatted as [ExpeL rule weight=...] .... This representation exposes the rule’s persistence weight alongside its content. The observation is the structured state summary supplied by the adapter.
The action parser accepts a mapping directly or JSON text, including a fenced JSON response. It accepts either a nested action mapping or the mapping itself. A singleton {"noop": true} or {"noop": 1} becomes the adapter’s no-op marker. The action parser validates the response mapping; task success is evaluated from environment observations.
Reflection receives the stage episode: instruction, status, steps, actions, visible_state, visible_state_timing, and method. The state is explicitly labeled as the last pre-action observation, and the action list includes each returned action, including repetitions. The reflection parser accepts insight or reflection for the insight, and operations or rules for the operation list. It normalizes the response into insight text and rule operations. The prompt requests up to four rule operations per reflection.
Table G2. ExpeL persistent artifact fields. Episode records, extracted insights, and rule-update history are stored separately.
| Field | Stored content |
|---|---|
| format | ExpeL memory schema identifier |
| record_count, insight_count | Sizes of the retained episode and insight lists |
| records | Stage episodes with action and feedback fields |
| insights | Whitespace-normalized reusable text |
| rules | Rule objects containing text and integer weight |
| rule_events | Normalized operations, list_full, and the resulting rules snapshot |
The artifact therefore preserves both the interaction record and the rule state used for subsequent decisions. The loader validates the artifact’s format identifier.

G.5 Evaluation algorithm
The following pseudocode summarizes the common orchestration contract. Source interaction, artifact persistence, environment reset, and target evaluation are separate operations. The same control flow can host parameter updates, text memory, or executable skills, provided that the permitted persistent state and input interface are declared.
At the task level, evaluation first observes the initial state, then alternates action and predicate evaluation until a terminal condition is reached. At the chain level, the runner applies the selected profile policy and records the first non-passing stage. At the experiment level, matched roles are combined within a seed before aggregation. These layers align environment execution, task success, and experience comparison at their respective units of analysis.
