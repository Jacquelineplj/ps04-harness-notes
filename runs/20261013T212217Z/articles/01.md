# The Harness Became the Variable: What Changed This Month

This month the harness stopped being a design opinion and started being a measured independent variable. Three independent strands — a controlled experiment, a state-based benchmark, and a batch of vendor orchestration primitives — converge on the same conclusion: harness choices now move solve rates and cost by large margins, and the signals most teams use to detect whether a change helped are miscalibrated.

## The measurement: a harness substituting for model capability

The clearest new evidence comes from a 13 October post on Martin Fowler's site, written by a Thoughtworks practitioner, comparing coding agents building the same API service with and without a behavioral harness, ten runs per condition. The frontier model passed every external evaluation in both conditions; the cost-optimized model succeeded in 3 of 10 unharnessed runs and 10 of 10 with the harness [01-c1]. The economics are the part worth staring at: the harnessed cheap model hit the same 10-for-10 acceptance as the unharnessed frontier model at roughly 33% lower cost per run, $0.273 versus $0.406 [01-c2].

We read this as the first widely circulated result that treats the harness as the thing being varied rather than the thing held constant. The author frames it as a revised, conditional hypothesis rather than a law: what changes with model capability is not whether independent sensors are needed, but when they run — continuously during development for weaker models, once as a final acceptance gate for frontier ones [01-c8].

## The instrument problem: clean exits that aren't

If the harness is a lever, you need an instrument to tell whether pulling it helped. A 3 October write-up of ThinkingBox, posted to Hugging Face, argues the instruments most teams use are broken. ThinkingBox grades agents on terminal backend database state instead of tool calls, and reports that across its executable-check failures, 67.24% still terminated cleanly, invoked a state-changing tool, and reported no final tool error — a trajectory-based grader would have scored those runs as fine [01-c3]. Its summary line is blunt: a trajectory is a claim, database state is the evidence [01-c8].

Taken at face value, that means the completion signal baked into most agent loops — no exception, no tool error, agent says done — is wrong on roughly two thirds of failed runs in this benchmark. That is not a tuning problem. It is a claim that the harness's self-report is not admissible evidence.

A smaller, more immediately actionable version of the same point appeared in a 12 October Arize walkthrough using Harbor and Phoenix. Changing one tool description eliminated 51 unnecessary skill loads and cut a benchmark run's cost from $11.85 to $8.34, with correctness unchanged [01-c6]. The authors emphasize that the score passed every time; only the trace revealed the waste [01-c6]. Score-only evaluation would have shown nothing.

## The levers vendors shipped

Anthropic announced dynamic workflows, discussed in a 12 October Latent Space write-up: Claude plans and writes its own orchestration program, which launches sub-agents, collects results, and manages information flow, replacing the prior requirement that developers configure a coordinator and a roster of sub-agents [01-c4]. Pre-configured specialists can still be passed in [01-c4]. This is a vendor announcement with no independent measurement attached.

Microsoft shipped harness-layer primitives in Agent Framework in late September: managed semantic memory via a Foundry memory provider, and Hyperlight-sandboxed CodeAct execution with an explicit isolation boundary — Hyperlight isolates model-generated code, while registered application tools execute in the application's runtime and retain their own permissions [01-c5]. Foundry hosted agent isolation separates two controls, user isolation (whose data may be used) and session isolation (where code and files live) [01-c5].

The most useful Microsoft item is not an announcement but a measurement. A 16 September post compared A2A specialist agents against distributed skills over MCP with execution traces side by side: moving specialist instructions into the orchestrator cut model calls from six or seven to three per request, but consumed about 22% more total tokens across three runs — fewer model calls did not mean less cumulative context [01-c7]. The author is careful that this reports tokens, not dollars, and does not isolate architecture from cache effects [01-c7].

## Where this is weak

The counterargument is sample size and generality, and it is strong. Fowler's experiment is one greenfield Java service with an unusually detailed brief; the author explicitly flags that legacy code, other languages, and vague requirements are untested [01-c1]. ThinkingBox tasks are synthetic reconstructions [01-c3]. The vendor items — dynamic workflows, Agent Framework, Foundry isolation — are announcements and product documentation with no independent measurement at all [01-c4][01-c5]. No one outside the vendors has reported whether self-planned topologies raise or lower failure rates, or whether managed memory recall is any good. Missing entirely: open-source maintainers running these harnesses at scale, security researchers assessing the new self-planning orchestration surface, and non-US builders. Nearly all vendor evidence here is US commercial.

## What this means for builders

The asymmetry is the story: the levers arrived ahead of the instruments [01-c8]. Vendors shipped self-planned orchestration, sandboxed code execution and managed memory this month; the measurement work came from a consultancy experiment, a research benchmark, and an observability vendor's walkthrough [01-c4][01-c5][01-c6]. Before adopting dynamic workflows or managed memory, build the state-based check first — grade the backend, not the transcript [01-c3] — and keep traces next to scores, because cost regressions hide behind passing suites [01-c6]. And if you run a cost-optimized model, the harness may be the cheaper purchase than the bigger model [01-c2].
