# The Harness Grew Up: What Changed in Agent Engineering This Month

The most consequential agent-engineering developments this month all answer the same question from different directions: where does the state a running agent depends on actually live, and who is accountable for it? Vendors answered by moving orchestration into the model; measured research answered by grading the environment outside it — and the research is the part you should act on first.

## Vendors moved orchestration into the model

Anthropic announced "dynamic workflows," in which the lead agent writes its own orchestration program — launching agents, collecting results, managing information flow — instead of the developer configuring a coordinator and a roster of subagents [01-c1]. This was covered on Latent Space on 12 October, based on a presentation with audience Q&A rather than a controlled study. The caveats came from the presenters themselves: Anthropic's Stall said the model does not know its budget while running, and Avilla said that in their watchlist-scanner comparison flows cost "much more" than a single-agent approach, while being "much more effective at finding all of the details" [01-c2].

Microsoft published a structurally opposed pattern in a 16 September post: rather than spawning a specialist agent loop, specialist instructions are loaded into the orchestrator's context as distributed skills over MCP [01-c3]. The author's own three-pair trace comparison showed three model calls for the skills path versus six or seven for the A2A path — and explicitly disclaimed being a controlled performance or quality study [01-c3]. Microsoft also shipped a Foundry hosted-agent isolation model that separates user isolation (whose data may be used) from session isolation (where code and files persist), with the pointed note that a hosted session is not a conversation: a conversation holds message and tool-call history, a session holds sandbox compute and persisted files [01-c9].

Read these together and the direction is clear: both vendors are relocating the state the next step needs. Anthropic puts it on a shared filesystem between subagents; Microsoft puts it in one context, or in an explicitly named sandbox.

## Measurement moved the other way — toward the environment

The strongest evidence this month graded outcomes, not trajectories. The ThinkingBox benchmark, published 3 October, grades agents on terminal backend database state. In a common-set ablation of 121,680 valid trials, 79,853 attempts failed the executable checks — and 67.24% of those failures still terminated cleanly, invoked a state-changing tool, and reported no final tool error [01-c4]. If you are monitoring final-message success and tool-error rates, that is roughly two-thirds of your failures invisible.

Two papers posted 9 October attack the reliability layer directly. RATED reports that reranking tool retrieval with a contextual bandit updated from live execution feedback cuts fault selection rate from 86.2% to 2.9% under a 30% injected failure rate, at under 1 ms of added latency [01-c5]. A sandbox-snapshot search paper reports that full-machine restoration beats source-only restoration only when progress lives outside the repository: on a task whose state sat in a SQLite database, snapshots solved 4/5 attempts while git-diff and clean restarts solved 0/5 [01-c6].

And Arize, in a 12 October walkthrough of testing tool descriptions with Harbor and Phoenix, reports that changing a single tool description cut Codex's unnecessary skill loads from 51 to zero and lowered a benchmark run's cost from $11.85 to $8.34, with correctness unchanged on the benchmark [01-c7].

## The thread

We read these as one argument, though no source frames it this way: the design question underneath all of them is where state lives and who owns it [01-c8]. Vendors answer with shared filesystems and relocated instructions; the measured work answers with execution feedback, terminal database state, and environment snapshots [01-c8]. That is an interpretation, not a finding. But it suggests harness builders who treat context management as prompt assembly are solving the wrong layer.

## What this evidence cannot carry

The orchestration news is entirely vendor-sourced and none of it carries independent measurement. Microsoft's comparison is three request pairs on one demo, and says so [01-c3]. Anthropic's cost claim is a presenter's verbal characterisation, not a published figure [01-c2]. On the research side, each result is a single study on a specific task distribution: ThinkingBox's tasks are synthetic reconstruction, the snapshot paper's headline contrast rests on one custom SQLite task against 4/5 and 0/5 attempt counts [01-c6], and RATED's dramatic fault-selection drop is measured under injected outages rather than observed production failure modes [01-c5]. Arize's cost reduction is one run on 18 questions [01-c7]. We have no independent replication of any vendor claim here, and no voices from open-source orchestration maintainers or from operators running these patterns at scale past a quarter.

## What this means for builders

Treat observable terminal state — not the agent's final message — as your unit of evaluation, and assume today's success metrics are overstating reliability by a wide margin [01-c4]. Before adopting model-written orchestration topologies, note that the cheapest wins this month were unglamorous: one tool description rewrite [01-c7], retrieval reranking on execution feedback [01-c5], and knowing whether your task's progress actually lives in the repo [01-c6]. Those are measured; the orchestration shift is, so far, announced.
